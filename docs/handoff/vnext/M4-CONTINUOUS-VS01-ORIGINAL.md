## 二、这次需要真正改变的架构职责

我独立确认了三个关键现象。

### 1. Domain Gate 和用户目标完成被混为一谈

当前 S3 的 `after_gate()` 将 `DIAGNOSED`、无进展和预算耗尽放在同一个报告终止判断里。

这就相当于：

> 业务诊断已经形成，所以用户的当前问题也应该结束。

但两者不是一回事。

例如正式诊断已经判定回调被接收，用户仍可能继续问：“昨天那次 503 后来是不是重试成功了？”

Domain 可以保留原诊断；Agent 仍然需要决定是否查询历史。

我批准的改变是：分离业务事实裁决与用户目标完成判断，而不是继续在 Gate 外面加例外。

### 2. 多候选记录存在，但决策反馈不完整

当前 `S3Nodes.model_call()` 会记录多个 Tool Calls，却只返回 `calls[:1]`。其他候选标记为 `NOT_SENT_RECONSIDER_AFTER_OBSERVATION`。

同时，Prompt 要求每轮只选择一个工具，Provider 绑定也设置了 `parallel_tool_calls=False`。

这意味着问题不只是切片操作本身，而是模型选择、执行记录和下一轮反馈没有完整形成闭环。

可以继续串行执行工具，但剩余候选必须被明确重新评估，不能自动执行，也不能无声消失。

### 3. 最终交付没有独立得到保障

现有 C1 的真实失败已经足够明确：新 Run 获取 `QUEUED` Observation 后，因为 Task 累计模型预算耗尽，最后留下空白 `PARTIAL`。

这次不能只处理工具循环而忽略交付。

我把“用户最终获得有依据的答案或明确的未知事项”提升为新里程碑的必要验收条件。

## 三、下一阶段应该实现什么？

业务目标：订单回调连续自主调查

用户不需要知道内部 Event、Run、Gate 或 Transport Attempt 的结构，也能逐步查清自己关心的回调。

1. “上次回调失败了，后来怎么样？”

   Agent 可以根据当前绑定订单定位可能的事件、查询可信历史，或在关联无法判定时请求必要澄清。
2. “不是这次，我说的是昨天那次。”

   Agent 应更新调查关注点，重新核对适用的 Event，而不能继续拿上一条事件的成功记录回答。
3. “那现在处理完了吗？”

   Agent 根据当前合法 Evidence 给出结论。若只能确认投递被接受而不能确认业务处理完成，就应明确告诉用户。

这条旅程是验收示例，不是规定的执行顺序。

用户单纯询问 HTTP 202，已有有效协议就应允许直接解释。用户只提供模糊时间，Agent 可以先澄清。取得充分证据后也可以立即结束，不必为了表现智能继续调用工具。

这是与固定 Workflow 的本质区别。

## 四、Gold 与预算，我作出两个具体决定

第一，六对 Gold 都保留，但不把它们转化为六条编码路径。

首个实现重点验证 P2（事件关联）、P3（历史完整性）和 P5（当前接收状态）。P1、P4、P6 仍属于最终里程碑验收，不删除、不降低原判据。

P2/P3 原定的四个留出实例继续封存，不用于 Prompt 调优。开发应使用独立样例；留出失败必须如实记录，不能看完失败后针对同一留出集反复修正再声称独立成功。

第二，允许有界预算实验，但不预先认定新额度。

现有 8 MODEL / 6 MCP 作为基线。首轮允许在隔离实验中预注册并比较两个候选额度，例如 12/8、16/10；这只是实验上限，不是生产默认值，也不表示这些数字一定合理。

每个连续 Task 都必须累积记账，Worker 重启不重置。分类器、可见 Chat 与 Investigator 的 Provider 成本分别统计并汇总。最终额度由真实旅程、无效循环负例和成本结果决定，不能为某个测试样例特判。

正常旅程需要有用回答；真正达到资源上限时，可以由可信执行层交付已确认事实与未知事项，但不能把长期依赖兜底当作自主策略成功。

# OpsPilot · M4 Continuous Investigation · Vertical Slice 01

**决策：APPROVED_FOR_IMPLEMENTATION_WITH_LIMITS**

**基线：** `main@85be293342529de85b40507b9c90c75bc1a77b38`

**目标：** 用户能够通过连续对话核对绑定订单的回调历史、修正事件关联、取得当前处理事实，并收到有来源的答案或明确的未知事项。

## 1. 开工与冻结

从最新远端 main 建立独立分支。开工重新核对 Git 状态，读取当前 North Star、AGENTS、订单回调提案、C1 Gold、相关安全合同及遗留门禁。

利用现有提案在实现前冻结首轮可执行 Gold 和 RED，不另做一轮完整提案修订。

首轮以 P2、P3、P5 的独立开发样例为重点；P2/P3 原四个留出实例严格隔离。原六对 Gold 的产品目标保持不变。

## 2. 真实历史事实能力

在现有 S3 业务领域内最小增加追加式 Transport Attempt 事实记录。

要求：

- 一个 Event 可对应多个独立 Transport Request。
- 真实重试保持 Event ID，新的 Event 不能冒充旧 Event 的重试。
- 记录可信来源、尝试顺序、时间、HTTP 响应或传输结果及必要 digest。
- 只有可信测试业务发送端可以产生真实 HTTP 尝试；Agent 只有绑定资源内的只读查询权。
- 历史缺失、超时及发送和入库之间的未覆盖窗口必须表达为未知，不得伪造完整审计历史。
- 保留现有快照与正式 Diagnosis/Handoff 权威。

实现最小有界 MCP 历史查询，复用现有 TaskBinding 和授权规则。不得扩建发送平台或给予 Agent 重发能力。

## 3. 调查循环的职责简化

基于现有 `investigator.py` 和 `S3Nodes`，实现观察驱动的合法继续、澄清、回答或结束。

重点：

- `DIAGNOSED` 不再单独决定最新用户目标已完成。
- `MCP_NO_PROGRESS` 应成为可解释的反馈，不自动等价于整次调查失败。
- 模型无 Tool Call 时，区分直接回答、请求澄清、异常无进展，不能一律视为成功。
- 多个合法候选允许串行处理；每次观察后，模型能明确保留、修改或撤回尚未执行的候选。
- 不自动执行旧候选，不绕过工具授权，也不规定唯一查询顺序。

同步审查 S3 Prompt 中“每轮恰好一个工具”的要求与真实模型工具返回行为，保持决策和执行语义一致。

只在本次实际触及的地方处理 `s3_investigation.py` 对 `investigator.py` 私有工具函数的反向依赖。可复用或抽取必要的共享小函数，不进行全仓重构。

## 4. 用户可用的结果交付

正常完成时，回答直接针对用户当前关注的 Event 或问题，简要说明结论、依据、时间、未知事项及下一步。

在预算耗尽或 Provider 失败时，若已有可信事实，交付来源可追溯的简短部分结果；不伪造未观察到的过程，也不把空白 `PARTIAL` 视为达标。

保留当前 `ANSWERED/PARTIAL/NOT_COMPLETED` 语义，不修改正式业务 Diagnosis。

工作台应展示用户可读的进度、结果与可展开来源，不将内部 Gate/Run/预算状态作为用户理解问题的前提。

## 5. 有界成本实验

以原 8 MODEL / 6 MCP 为基线。

隔离实验中最多比较两个事先记录的候选 Task 上限（建议 12/8、16/10），不能无限增加试验配置。

保持 Task 累计记账、Run 内防循环和恢复不重置；分类器、Chat、Investigator 的实际 Provider 请求与 Token 成本全部记录。

未经主 Agent 新裁决，不将实验上限直接设置为正式默认值。

## 6. 双向测试和真实用户旅程

测试必须同时证明：

- 同 Event 重试与不同 Event 不会混淆。
- 历史存在可以正确关联，缺失时不会推断出伪造历史。
- QUEUED 与 PROCESSED 导致不同的有依据回答。
- 用户更正事件后能改变调查方向。
- 有效协议可直接解释，不强制历史查询。
- 一次无结果可以合理换方向，但无效重复最终受预算限制。
- 多候选不会静默丢失，也不会未经重评估自动全部执行。
- 错订单、跨租户、授权撤销和旧 Run Evidence 借用被拒绝；合法同 Task 查询继续可用。
- 可信事实已经取得但模型额度耗尽时，不出现空白的伪成功结果。

先保存 RED，再实施并保留 GREEN、失败和完整回归。

至少完成一条真实 Provider + MCP + HTTP + Web 连续用户旅程，能看到模型选择、工具观察、后续判断与最终用户回答。

## 7. 效果分析与停止线

首先报告用户以前做不到、现在能完成的具体任务，附真实对话和来源。

其次报告 Agent 自主决定了什么、观察为何改变行动。

再展示新增或修改代码、替换了哪些混合终止条件、减少了哪些重复职责，以及仍然存在的局限。

保留完整六对 Gold 及公平 R/H/A 的最终里程碑要求；第一轮可先做有界对照，不以 A 必须胜过 R/H 为目标。

**本切片停止线：** 独立开发场景中的连续业务调查真正跑通，Agent 能根据观察调整合法行动，用户得到正确、有来源的结果或明确缺口；安全和成本边界成立，并保留可复查的真实 Trace。

最终提交候选分支、Base/HEAD、Diff、RED/GREEN、成本、完整失败及原始 E2E 证据。

状态仅为 `ACCEPTANCE_CANDIDATE`，由主 Agent 独立验收。未经批准不得合并 main、开展新受控写能力或扩建 Planner、Goal Manager、多 Agent、通用 Runtime。

这次我希望彻底改变一种开发惯性：

过去我们比较容易形成“发现一种失败 → 新增一条限制 → 增加测试 → 宣布修复”的循环。

接下来应当是：

发现用户尚未完成的业务目标 → 判断缺少哪种事实或自主决策能力 → 在已有职责中补齐 → 用真实用户旅程检验 → 删除不合理的旧限制。

最终项目是否变得更好，不由新增了多少代码、多少状态机或多少工具决定，而由用户是否真的能够完成此前无法完成的任务决定。

这次可以进入开发了。
