# 订单回调连续自主调查：业务冻结提案

**状态：** `DRAFT_FOR_MAIN_AGENT_REVIEW`，不是开发授权或已冻结 Gold。
**事实核验基线：** `main@f6db02b331ce4279ce0b00063bf19b917af423ff`。
**目标：** 用户在同一 Task 连续追问“哪次回调失败、后来哪次被接受、现在是否处理完成”，Agent 能查明 Event/Transport Request 关系，依据新观察调整下一步，并给出有来源的时间线与明确缺口。

## 1. 已确认的业务能力缺口

`s3_deliveries` 是每订单一行的当前投影，只保留一个 Event、Transport Request、HTTP 响应和 `attempt_count`（`opspilot/domain/s3.py:67–74`）。Fixture 最多执行一次真实接收方 POST，返回内存 Trace，再用 `INSERT OR REPLACE` 写当前投影；没有可追加的回调发送历史（同文件 `305–408`）。`s3_http_observations` 记录订单 GET，D2 Observation 记录 Agent 查询，两者都不能冒充回调 POST 尝试。当前 MCP 只查询 current order/delivery/receiver（`opspilot/domain/s3_mcp.py:39–54`）。

因此当前能力不能证明“同 Event 第一次 503、第二次 202”，也不能用最新 Event 的 202 证明旧 Event 成功。上一轮的[只读可行性核验](../evidence/vnext/m4-c1-final-wiring/S3_FACT_FEASIBILITY.md)保留为依据；本提案没有实现表、工具、循环或模型预算变更。

## 2. 最小事实模型与合法只读入口

只补充一个 **append-only Transport Attempt 事实存储职责**，暂名 `s3_transport_attempts`；现有快照继续承载当前状态，不迁移 Diagnosis/Handoff 权威。

| 字段组 | 拟冻结内容 |
|---|---|
| 作用域 | `tenant_id/service_id/integration_id/order_id`，全部来自可信发送端和当前 TaskBinding；模型不能赋权或指定任意资源。 |
| 关联身份 | 不可变 `attempt_id`、稳定 `event_id`、Event 内 `attempt_no`、独立 `transport_request_id`。请求 ID 和 `(scope,event_id,attempt_no)` 唯一；重试保留 Event ID，新 Event 不接在旧 Event 序号后。 |
| 发送事实 | 可信目标引用、订单/协议版本、请求或载荷 digest、开始/观察/入库时间、发送来源及来源记录 ID。不得存凭据或任意 URL。 |
| 实际观察 | `HTTP_RESPONSE/TRANSPORT_ERROR/OUTCOME_UNKNOWN`、可空 HTTP 状态、脱敏响应摘要及 digest。超时只能证明未获得确定响应，不能证明接收方未收到。 |

只允许可信本地测试业务发送端把**实际 HTTP 尝试**写入该记录；模型、聊天、Memory 与 Knowledge 不得补写。首个切片准备历史所需的发送由测试环境独立执行并记录，不给 Agent 新增重发能力。

建议每条已完成观察不可修改，重复来源以身份/digest 幂等裁决。首版只承诺“已知且持久化的观察”，查询必须返回覆盖时间范围、缺口/未知状态及来源；没有记录不等于没有发送。发送与落库之间的崩溃窗口如果尚未被可信来源覆盖，必须报告历史不完整，不能声称完整投递审计。主 Agent 应在开发卡中冻结该取舍；不借本切片建设发送 Runtime。

拟新增一个有界只读查询，复用现有 S3 TaskBinding/当前授权检查：从当前绑定订单枚举或过滤相关 Event/Attempt，返回稳定排序、限量/截断标记与实际关联。Event/Request 过滤值必须属于该绑定订单；无任意 tenant、URL、凭证参数。跨租户、错订单、撤权读取继续 fail-closed；同 Task 的合法历史查询必须可用。历史内容和本次成功读取的 Observation 分别追踪，不能继承旧 Run 的当前性。

这些事实仅用于有来源的只读补查及解释。正式 S3 Gate、Diagnosis、TaskControl、审批和 Handoff 资格保持原合同；历史 202 不能直接形成当前诊断、恢复结论或交接授权。

## 3. 连续旅程与 Agent 决策空间

建议旅程：“订单没回调” → 查看绑定订单及实际相关 Event → 用户追问“刚才那次 503 后来呢” → Agent 自选历史或当前状态查询/协议查证 → 用户问“那现在处理完了吗” → 当前 Run 合法再取证，或明确缺口。

允许 Agent 根据输入和中间观察选择先查快照还是历史、缩小到相关 Event、查询接收状态或适用协议、在多个候选仍有歧义时澄清、证据足够时直接解释、预算内继续或停止。不规定唯一工具顺序，不强制调用 Knowledge/Skill/Memory。现有合法资产可提供方法提示，其引用需重验证，当前事实始终优先。

可信程序只裁定资源、授权、记录关联、Observation 当前性、现有预算和正式业务结果。已有 C1 持久回答续接与 TaskControl 纠错流程继续复用；不建设 Planner、Goal Manager、通用 Runtime 或新治理平台，不增加模型/MCP 预算常量。

## 4. 拟冻结的成对业务 Gold

各对保持描述或关键事实可比较；下表是待审判据，不覆盖旧 Gold。历史不完整是有效业务结果，不能为了全绿补造记录。

| 对 | 配对事实/措辞 | 必须回答或采取的合理行动 |
|---|---|---|
| P1 同描述、不同投递事实 | 同 Event E1 的真实尝试分别为 503→202，对照为 503→503；用户均说“订单没收到回调”。 | 前者继续核查协议/接收处理，后者说明已有证据支持的投递失败及处理方向；均不能把 HTTP 接受等同处理完成。 |
| P2 同 Event 与不同 Event | E1/R1=503、E1/R2=202，对照为 E1/R1=503、E2/R2=202。 | 区分同 Event 重试被接受与另一个 Event 被接受；不得用 E2 的响应证明 E1 成功。 |
| P3 历史完整与不足 | 两次实际观察均可查，对照只保留最新 202 快照或缺少第一次观察。 | 前者给可核查时间线；后者指出不能证实第一次响应/次序，不从 `attempt_count` 猜测。 |
| P4 同事实、不同自然语言 | “下游一直没收到回调”与“是不是重发后就好了”，底层事实相同；均接续同一后续追问。 | 结论一致、关联正确；允许不同合法调查顺序，代词追问不要求用户重复文档或 Event 名。 |
| P5 传输相同、处理不同 | 最新 202 与协议相同；接收方分别仍排队/已经完成。 | 当前事实决定等待、联系处理人或确认处理完成；引用当前证据，不能只复述历史 202。 |
| P6 引用改变 | 同 Task 引用的协议仍适用，对照为其版本失效。 | 有效来源足够时允许直接解释；失效协议只能作为历史线索，应查当前合法版本或明确缺口。 |

上述 12 个实际实例中，P2/P3 的四例作为留出：使用未参与调优的订单、Event/Request ID、措辞及时间，冻结后不参与 Prompt 调优。另设权限撤销、错订单/租户、跨 Run 借用、重复读取及恢复安全负例，单列分母，不能与主业务正确率平均。正式 Gold 需列出实际 fixture 初态、允许结论、必需来源、禁止动作和停止条件；Gold/期望标签只供离线评分，不能进入在线 Agent、MCP 或 Gate。

## 5. 最终用户回答与公平 R/H/A

最终回答应直接覆盖用户所问的那次 Event，列明已查到的每次 Transport Request、顺序/时间、实际响应和引用；区分“投递被接受”“接收方处理完成”“已交接”。说明哪项新观察改变了判断，哪些历史仍未知、需要什么合法补查。没有当前事实或真实回执，不得声称恢复、完成或交接。沿用 C1 `ANSWERED/PARTIAL/NOT_COMPLETED` 的只读结果，不用回答文字覆盖正式 Diagnosis。

- **R：** 合理的确定性解析和有条件规则调查，可澄清、提前停止；不得故意扫描所有工具或读取 Gold 答案。
- **H：** LLM 归一化真实用户线索，调查策略与 R 相同；归一化结果必须影响合法查询选择。
- **A：** LLM 在同一合法工具、资产和预算内，根据新观察自主选择下一步、澄清或停止。

三组共用每例独立重置的 Domain 初态、输入旅程、模拟用户澄清事实、权限、只读工具、协议资产、Gate、停止条件及评分器；现有 Task 累计预算不重置、不放大。重复实验使用等价独立 Task/数据库实例，同一连续旅程始终共用自己的累计预算，不能清零原 Task 的 Attempt。冻结模型/Prompt/工具 Schema/依赖版本和试验次序；建议上述 6 对共 12 例，每组每例一次主运行，再以单独预算预注册模型重复次数，所有尝试和失败均入分母。历史发送准备与 Agent 查询 Trace 分开，禁止挑选成功重跑替代首次结果。

分报用户目标完成、Event/Request 关联正确率、当前/历史结论正确率、有效证据覆盖、澄清负担、工具及无效调用、Token、延迟和成本；安全失败独立判负。依据实际出站消息、模型选择理由/可观察行动和下一次工具调用核对资产是否改变下一步，不以多调用、多推理或 A 胜过 R/H 作为预定成功条件。只有通过真实 Provider、MCP、HTTP 和连续 Web 旅程，才称已证明业务效果。
