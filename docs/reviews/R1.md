# OpsPilot v0.1：独立架构评审 R1

评审日期：2026-10-17（北京时间）

评审对象：[架构评审稿 v0.1](OpsPilot_ACE48996E6B69EE884AEE48EAEE6BDAEE592_v0.1.md)。下文位置指该文件的章节和行号。已完整阅读该稿，并对照当前 README、TASKS、AGENTS 及 LangGraph/MCP 官方资料。

**结论：Approve with conditions（方向有条件通过）；当前 v0.1 尚不具备交给 Luna 全面实施的冻结条件。** 先解决 B1–B5，再冻结实施基线。不要求重选领域，也不要求引入更多基础设施。

本轮是设计评审，不是实现审计。尚无业务代码可供验证，未运行模型、MCP 或恢复实验；旧项目的 72 题数字仅作为稿件背景，没有重新核验。以下替代方案都是供主 Agent 回复的评审建议，不代表已经达成共识或修改了原稿。

## 总体判断

| 关注点 | 判断 |
|---|---|
| 业务选题 | S1 足以支撑工程深度。API 鉴权故障可以包含多种解释、当前事实与历史经验冲突、真实受控变更，不需要 S3 才能证明深度。首要用户建议固定为负责客户接入问题的技术支持/后端工程师。 |
| 主 Graph | 固定业务阶段 + 动态只读调查循环合理。当前缺的是可执行分支、状态所有权和结束判据，不是节点数量。 |
| 模块边界 | 大体合理，但逻辑模块不应全部变成服务或通用框架。在线 Verifier 与离线 Eval 的数据访问边界必须分开。 |
| 七天范围 | 按 28–35 小时且有熟悉框架的实施者，收缩后的 P0 有机会完成，风险仍高；按原任务表 21 小时核心时间不宜承诺全部完成。 |
| 面试价值 | 证据改变调查路径、审批过期、提交成功但响应丢失、记忆失效等值得追问。工具数量、空目录数量和框架名本身不能证明能力。 |

## 必须修改：五个冻结阻断项

### B1 · 固定 S1 的因果链、唯一修复动作和业务完成定义

**位置：** §2.2–2.3，行 56、66；§3.1，行 81；§14，行 402。

**问题与影响：** “旧密钥版本导致 401”尚未说明旧版本位于调用方还是被调用方，配置更改如何真正影响请求，以及验证使用哪一个身份。实现方可能做成更新一个 SQLite 字段，再读取同一个字段作为“恢复成功”。同时，§14 允许退回只写工单，会悄悄改变已经承诺的受控恢复目标。

**最小替代方案：**

1. 选一个 Demo 业务 API 和一个调用方集成配置。调用方配置保存 `credential_ref`；测试凭证在工具侧本地解析，模型只见引用和版本。API 实际校验凭证及主体是否启用。
2. S1 正例：API 当前接受新凭证，调用方仍引用旧凭证；通过该调用方发出的业务探测实际失败。唯一修复动作为“将指定集成配置切换至允许列表中的凭证引用”，附配置预期版本。
3. 正例处置后，重新通过同一集成配置、同一主体访问同一业务端点，核对状态码和预期业务响应。修改配置的回执、数据库中的目标值、通用 `/health` 都不能单独代替这次探测。
4. 负例：近期发生过变更，但主体被禁用；不得通过换凭证或重新启用主体绕过停用决定。Agent 可以正确调查并转交，不能算作已恢复。
5. 首周可用 Python Demo；只有现成 Java 样例能直接复用时才选 Java。无需两个完整 Java 工程、Redis 或监控平台。
6. 测试驱动器可设置故障并持有预期答案；Agent 工具只能查询业务可见事实。禁止把 `expected_root_cause`、`correct_action` 或样例分类暴露给模型/在线 Verifier。业务系统明确记录的错误原因可以作为证据，但不能伪装成模型自主推理能力。

**完成语义：** 区分任务结束与服务恢复。建议保留现有任务生命周期状态，另设业务结果 `RECOVERED / NO_CHANGE_NEEDED / ESCALATED / UNRESOLVED`。配置修复成功但工单写回失败时，业务可以已恢复，交付仍未完成；继续交付不能再做修复。Memory 写入失败不应撤销已经成功的业务交付。

**验收：** 去掉 LLM，先人工调用同一套业务工具重现“失败请求→真实配置变更→成功请求”；主体禁用负例不能被该动作修好；探测不能使用独立管理员凭证。

**冻结交付物：** 一页 S1 场景契约，写清主体、资源、故障注入、动作参数、前置条件、验证断言与终态。讨论整理预计 1–2 小时；实现工作已包含在后文总工时中。

### B2 · 定义状态真相来源与审批—动作—业务写入的一致性协议

**位置：** §3.2，行 89–91；§4.2，行 133–145；§5.2，行 166–168；§6.1，行 176。

**问题与影响：** Checkpointer、Task State、审批、动作服务、业务配置和工单都持有部分状态，但尚无唯一写入者和冲突解决规则。仅有 `idempotency_key`、`approval_id` 字段，不能阻止响应丢失后的重复写入，也不能阻止旧批准被用于新参数。稿件没有独立 Plan / Approval 契约，`ActionResult.status` 和 `side_effect_known` 的组合语义也未定义。

**建议的 P0 所有权：**

| 状态 | 权威来源 / 写入者 |
|---|---|
| 调查步骤、待办、阶段、当前计划引用、消息、预算 | LangGraph 检查点；节点返回受校验的状态更新 |
| Task 与 actor/scope/thread 的绑定 | 可信入口建立的不可随意变更的记录；用户查询和恢复先核对它 |
| 审批决定、动作执行结果、配置版本、工单 | 单个 Demo Domain 服务管理的 SQLite 业务表 |
| 原始证据、交付报告 | 持久化证据/Artifact 存储；检查点引用已保存的对象 |
| 跨任务经验 | 独立 Memory 表及受限读写函数 |

Task 查询接口可以投影 Graph 状态，但不要再维护一套由 API 随意修改的“主 Task 状态机”。状态存储可以用同一 SQLite 技术，不意味着必须让 LangGraph 内部表与业务表共享一次事务。

**最小一致性协议：**

1. Plan 保存结构化动作、目标、预期资源版本、验证条件和内容摘要；新计划生成新版本。风险级别与审批要求由程序根据动作映射得出。
2. Approval 保存审批人、决定、任务、计划摘要、目标/环境和时间；绑定具体动作，不能只保存一个可跨计划使用的 `approved=true`。
3. 执行前再次检查主体权限、审批绑定与资源版本。资源已变化，拒绝旧计划并重新调查或交付差异；不能静默套用旧批准。
4. P0 让配置变更、动作台账及审批消耗由同一 Domain 服务在同一 SQLite 事务中处理：校验前置条件→更新配置→记执行回执→记录审批使用→提交。Demo API 读取已提交配置。
5. 对同一作用域和幂等键，相同请求摘要返回既有结果，不同摘要拒绝。检查已有结果前仍校验请求者作用域；“已消费审批”不能令原请求合法重放失去查询结果的能力。
6. Graph 在响应丢失或检查点未更新时，按原动作身份回查。查询不可用时保持结果未知，暂停新处置；不能把未知当失败并生成新键重试。
7. P0 同一 Task 只允许一个活动执行者；重复的批准/恢复请求受串行控制。独立任务同时改同一配置仍由版本条件阻止冲突。
8. 配置修复和工单交付是两个动作，分别幂等。工单备注使用 `(task_id, report_version)` 等稳定身份去重。MCP 只读，不必为本周引入跨系统事务协调器。

**审批边界还需明确：** “拒绝后零写入”应指零受限业务变更，而非零数据库写入；检查点、拒绝决定和审计仍须持久化。工单更新也属于业务写入：建议 P0 拒绝分支只输出本地调查报告，不更新业务工单。正常路径批准具体配置动作和明确的工单交付操作；若选择预授权的状态备注策略，也必须单独写清，不得隐藏在 Deliver 中。

**必须覆盖的故障点：**

| 故障点 | 预期结果 |
|---|---|
| 等待审批时退出 Agent 进程 | 重启后仍等待原计划审批，没有业务变更 |
| 业务事务提交前故障 | 无半写配置；同请求可安全续行 |
| 业务事务提交后丢响应 | 回查得到已提交结果，不产生第二次配置变更 |
| 收到回执但 Graph 未保存新检查点即退出 | 恢复后重放/回查仍只有一次变更 |
| 相同批准被重复提交，或旧批准配新参数 | 前者复用结果，后者拒绝 |
| 修复成功，工单写回失败 | 只重试交付，不再次修复 |

原文“审批前关闭服务”应改为“关闭 Agent 执行进程”，区分与 Demo API/MCP 服务停机测试。LangGraph 从中断节点重新执行；副作用应隔离并具备幂等性，这是官方明确提醒的行为。[LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

**冻结交付物：** 所有权表、Plan/Approval/Action 枚举与字段、单次提交时序、故障点验收表。讨论整理预计 2–3 小时。

### B3 · 将动态调查、证据门禁和 Graph 分支写成可执行契约

**位置：** §3.1–3.2，行 72–92；§4.2，行 133–154；§5.1，行 160–162；§10.2，行 294。

**问题与影响：** “有界”“明确证据”“不得无限重试”还不是条件边。仅绑定一个 Evidence ID 只能证明引用存在，不能证明它支持结论。现有字段清单也没有说明工具消息关联、证据如何合并、Plan 如何产生，以及谁能更新 `stage/status/budget`。Luna 很可能各模块自行补定义。

**最小替代方案：**

- 只有调查阶段交给模型选择只读工具、参数、补证和诊断假设；身份、预算、执行权限、路由门禁、审批和动作提交由程序控制。
- 诊断草案包含 `hypothesis_id/type`、支持/反对证据 ID、未解决问题、下一步建议。证据门禁返回 `READY / NEED_MORE / INCONCLUSIVE / NO_ACTION` 之一，不接收模型自行授权的“可以执行”。
- 为 S1 写少量明确谓词：证据属于相同主体/资源，版本仍有效，调用方引用与可用凭证版本不一致，主体处于启用状态，关键观测不矛盾。缺谓词对应证据就不生成可执行修复。门禁验证当前业务事实，不导入测试答案，也不宣称证明所有自然语言因果关系。
- Evidence 补上被观察资源/主体、事件时间或观测区间、结构化事实引用。`fetched_at` 只表示何时读取，不能让刚读到的旧日志变成当前事实。
- 工具原始结果先保存，模型摘要与原始事实分开。MCP/本地工具都关联稳定 `call_id`、`evidence_id` 和结果状态。
- Graph 内保留最小工具对话消息及 `tool_call_id` 对应结果；业务 Task State 不需要保存所有全文，但模型下一步必须能看到上一调用与 Observation 的正确关联。
- 对累积证据定义按 ID 合并/去重规则；对 plan、stage、status 定义替换与唯一写入者；模型只返回允许更新的结构。Graph reducer 默认行为不能靠猜测。[LangGraph State / Reducers](https://docs.langchain.com/oss/python/langgraph/graph-api)
- P0 建议默认最多 6 次只读工具调用、每次传输重试最多 1 次，重试计入总量；设置模型调用上限和每次请求超时。限额值可调，但必须唯一配置并跨恢复累计。严格用量需要在发起调用前持久登记/扣减；不宣称仅靠递归深度可保证实际 token 开销。
- 同一查询且无新环境信息时，不无限重复。调查耗尽→INCONCLUSIVE；明确缺少用户可补充的信息→WAITING_INPUT；两者分别处理。
- P0 验证失败后停止自动处置，交付失败证据并转人工。自动重新规划/补偿放 P1，避免每次失败都重置预算形成新循环。
- P0 取消只承诺执行前无副作用；执行已经发出时先回查，不能把 CANCELLED 当成业务回滚。

**最小主图建议（保持一个 Graph）：**

```text
load_context → investigate ↔ execute_read_tools
                    ↓ 提交诊断草案
                evidence_gate
                 ├─ NEED_MORE → investigate（共享剩余预算）
                 ├─ INCONCLUSIVE / NO_ACTION → report
                 └─ READY → make_plan → approval
                                      ├─ 拒绝 → 本地 report
                                      └─ 批准 → execute_or_reconcile
                                                   ├─ 未知 → 暂停并回查
                                                   └─ 已提交 → verify → deliver
```

Memory 候选在成功交付后尽力生成；失败记录为经验保存失败，不重放业务修复。Context Builder 是每次模型调用前使用的函数，不一定是额外图节点；权限/新鲜度在恢复后重新校验。

**验收：** 正例、迷惑负例、缺证据三种输入产生合理不同的查询/处置路径；引用存在但不相关、旧证据、相互矛盾证据均不能越过执行门禁；重启不重置逻辑预算；超时和验证失败有可预测出口。

**冻结交付物：** 节点输入/输出及字段写入者、条件边、诊断/门禁 Schema、三个场景的允许与禁止路径。讨论整理预计 1–2 小时。

### B4 · 固定身份信任边界，防止 scope 字段成为虚假的权限隔离

**位置：** §3.1，行 74；§4.2，行 133、139、142；§5.2，行 168；§6.1，行 174–176；§10.2，行 299。

**问题与影响：** 带 `tenant_id` 不等于授权。稿件未定义身份从哪里来、如何传到 MCP、谁能恢复 `thread_id`。若模型可填写租户、审批标志或目标 URL，程序即使对数据库做过滤，也可能是在按攻击者指定的作用域过滤。工具读写提示和注册状态同样不能代替授权。

**最小替代方案：**

1. 首周明确为本地可信操作者 + 两个预置主体/作用域。入口从受信配置绑定身份；不建设 SSO/RBAC 产品，也不宣称具备互联网多租户鉴权。
2. 模型可见工具参数不包含可任意切换的 actor、tenant、审批结果、风险级别。业务资源 ID 仍需在服务端与当前作用域核对。
3. Task 创建、查询、恢复和审批均通过同一所有权检查；不接受任意 `thread_id` 直接加载检查点。审批权限与请求发起权限显式定义，可在本地使用固定操作员映射。
4. MCP 首周固定一种传输，例如本地 stdio。服务端进程从可信启动配置获得允许作用域，查询再检查资源所属关系；若通过调用上下文注入作用域，必须确保它不能由模型参数覆盖。不能只在提示词里声称已绑定身份。
5. `probe_endpoint` 接收登记的 `service_id` 和允许的探测类型，工具侧解析固定端点与凭证，不接模型自由提供的 URL/Authorization。修复动作只接受允许的配置字段/凭证引用。
6. Evidence、Memory、Artifact 读取也按任务作用域检查；恢复旧检查点不能绕过当前撤销/有效性规则。日志和 Context 不保留原始密钥。

MCP 规范区分结构化工具结果与模型输出，要求服务端校验输入/访问控制；工具 annotations 也不能被无条件信任。接通协议不会自动提供项目的业务授权。[MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

**验收：** A 的任务不能读取 B 的证据/记忆、恢复 B 的 thread 或批准 B 的动作；直接构造越界工具调用也失败；工具文本要求切租户/跳审批时，程序侧限制仍生效。分别检查泄露的数据和实际业务副作用，不能只检查模型回复是否拒绝。

**冻结交付物：** 一张身份传递表、模型可见参数表、受限操作表及跨作用域测试。讨论整理预计 1 小时。

### B5 · 统一 P0、成功标准、时间预算与实施资料

**位置：** §6.2–6.4，行 186–194；§7，行 208–217；§8，行 223–231；§10，行 279–304；§14，行 402；现有 README/TASKS/AGENTS。

**问题与影响：** 同一项能力在不同章节既是“必须”又是 P1。测试还包含 P1 场景，时间预算从原来的 3 小时核心变成 4–5 小时。若不统一，实施和验收会采用不同的完成定义。

| 冲突 | 建议冻结口径 |
|---|---|
| §6.3 至少两个 Skill；§7.1 至少一个 | P0 一个按需加载的 auth Skill；第二个及“选择准确率”实验为 P1。只有一个时不声称实现复杂路由。 |
| Context Manifest 在 §3/§4 必须、§7.2 后置 | P0 记录本次调用的实际来源 ID/版本、Prompt/Skill/tool 版本；高级 token 分配、压缩比较和可视化后置。 |
| Memory 撤销/过期测试是硬要求，纠错/遗忘又在 P1 | P0 保留有效状态、过期过滤、手动撤销及当前事实优先；自动合并、复杂冲突治理和多级遗忘后置。 |
| S2 在 P1，但“最少 16 条”含回调故障 | P0 题集只围绕 S1 与基础控制边界；S2 不计入 P0 分母。 |
| 真配置修复是主目标，§14 允许只写工单替代 | 保留一次真实配置修复；只写工单可作中间里程碑，不能以相同名称宣称 P0 完成。 |
| 首周任务时间不一致 | 明确保障时间与选做时间，不能把原先的 1–2 小时选做自动变成每天必做。 |
| 当前 README/AGENTS 仍为旧工单建议方案 | 冻结后同步入口文件和每日任务指向唯一版本；旧稿保留历史身份，不让 Luna 在两套主线上自行选择。定时任务目前读取旧 TASKS，也应同步。 |

**P0 的验收应拆为三层：**

- **演示能力：** S1 正例能真实修复、负例能停止不当修复；跨重启恢复、一次 Memory 复用和按需 Skill 加载有实际证据。
- **控制约束：** 未批业务变更、越界、重复副作用、旧批准套新参数等测试全部通过；不能用其他成功案例平均掉这些失败。
- **模型任务表现：** 固定场景逐条记录结果；正确转交/拒绝不等于业务修复成功，分别统计“正确处置”和“实际恢复”。LLM 超时、Schema 失败、未完成均在预先约定的分母中，不临时剔除。

**冻结交付物：** 一张唯一 P0 清单、对每项的测试映射、工作量口径、资料优先级；不要求先完成所有实现。讨论整理预计 1 小时。以上各项讨论工作可一起完成，避免逐项召开评审。

## 建议修改：Major，不要求增加平台

| 编号 | 建议与理由 | 替代实施及验收 |
|---|---|---|
| M1 | 缩减部署层和抽象层。目录中出现 Service/Registry 不意味着要建设独立服务。 | 一个 Agent 应用、一套 Demo Domain、一个只读 MCP 服务；CLI 足以提交/审批/恢复。Context、Policy、Memory、Skill 用普通函数/模块。Agent 对外 FastAPI 可后置；Demo API 为验证因果链可以保留。 |
| M2 | 将真实模型、MCP 和 Checkpoint smoke 提至首日；D4 不应首次发现持久化不兼容。 | 先验证目标模型确实产生工具调用、MCP 可列出/调用工具、暂停后新进程能恢复。共享业务查询函数，本地与 MCP 只是薄适配，避免 D3 重写一套语义。 |
| M3 | 一个简单但真实的 Memory 流程优先。`confidence` 不能由模型自报值决定有效性。 | 首周只保存经验证的 episodic 经验；人工确认后 ACTIVE。按 tenant/project、问题类型、有效状态和版本条件筛选。创建新任务只传问题/工单，不把上次答案偷偷放在输入；重启后仍能复用。临时假设不入库。 |
| M4 | 在线 Verifier 与离线 Eval 分开。在线不能读隐藏标准答案；离线也不能仅因引用存在而判诊断正确。 | 在线检查预定业务契约和动作后状态；离线拥有场景预期、故障注入记录及评分规则。端到端样例和确定性控制测试分开报告。记忆 ON/OFF 是优先对照，控制初始数据库/记忆，禁止测试样例互相污染。 |
| M5 | 减少无收益的流程约束，固定有效契约而非节点布局。 | 删除“图结构调整必须说明为什么仅增加节点无法解决”；改为记录对外行为、状态兼容性、审批和回归的影响。只对这些语义变化记录简短决策，不为函数拆分/节点合并都申请 ADR。 |

补充两项落地细节：

- MCP 错误至少区分连接/超时、协议错误、工具执行失败，校验 `structuredContent` 与 `isError`；不要把“HTTP/协议成功”当业务成功，也不要把结构化结果与其兼容文本重复注入 Context。[MCP 工具结果和错误语义](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
- Graph 不必带完整历史，但当前轮的工具调用和结果要完整配对。启动时记录模型与依赖版本，恢复时不静默换 Skill/Prompt/工具语义；首周可以拒绝不兼容版本的恢复，无需实现通用迁移框架。

## 可以后置：不作为 P0 缺陷

| 编号 | 后置内容 | 保留的最小能力 |
|---|---|---|
| L1 | S2 回调、S3 Redis、第二 Skill、多个独立执行动作 | S1 正例 + 同症状反例 + 缺证据分支 |
| L2 | 向量数据库、记忆自动归并/衰减、自动生成 Skill | 一类结构化经验，手动确认、失效和作用域检查 |
| L3 | 通用上下文压缩器、动态 Registry、通用 Policy DSL | 小型来源清单、大结果引用、固定工具/动作允许列表 |
| L4 | 多 Agent、A2A、异步队列、分布式租约、自动补偿框架 | 单执行者、一项数据库事务动作、明确失败转交 |
| L5 | 生产多租户 IAM、监控平台、复杂前端、Trace 平台 | 本地身份边界、两个作用域负例、JSONL Trace、CLI |

作用域校验、当前事实优先、版本核对不能随这些平台一起后置；它们已被 P0 行为承诺依赖。

## 七天工作量与顺序建议

**判断：** 当前 v0.1 的全部“必须”难以稳定塞进七天；执行上述收缩后，才是可讨论的七天 P0。下面为规划估算，假定实施者熟悉 Python、已有可用模型账户并由编码工具辅助，不是已测工时或交付保证。

| 工作包 | 有效开发估算 |
|---|---|
| Demo 因果链、fixture/reset、环境 smoke | 4–6 小时 |
| 动态调查、证据门禁、MCP、状态契约 | 6–8 小时 |
| 审批、事务动作、恢复及故障注入 | 8–10 小时 |
| 最小 Memory、Skill 和上下文来源记录 | 4–6 小时 |
| 回归、一次对照、启动说明与演示 | 5–7 小时 |
| 合计 | 27–37 小时，另建议留 3–5 小时排错余量 |

学习源码、逐轮评审与业务环境排错会占用用户时间，不能把 Luna 的生成速度等同于用户已理解和验收。若只能保证 21 小时核心时间，建议延长到约 10–14 天，不靠取消真实处置、权限或恢复验收来凑“七天完成”。

| 相对日 | 核心交付 | 与原稿相比的调整 |
|---|---|---|
| D1 | S1 无模型业务闭环；真实模型、MCP、持久中断的小实验；确定 P0 样例及判据 | 技术未知项提前暴露；不先铺满空目录 |
| D2 | 动态只读调查 + 真实 MCP + 证据门禁，跑正例/迷惑负例 | 不保留两套本地/MCP 调查语义 |
| D3 | 计划、审批、真实配置操作、独立探测，首次完整闭环 | 首次集成提前，不留到 D7 |
| D4 | 响应丢失、重启、重复批准、版本变化、跨作用域检查 | 该日不过，不接更多业务场景 |
| D5 | 一个 Skill、最小 Memory、来源清单；新任务复用及失效验证 | 不做 S2、不做高级记忆系统 |
| D6 | 冻结 P0 回归运行、逐例失败分析、Memory ON/OFF 小对照 | 样例标准已在 D1 定义，D6 只补齐与执行 |
| D7 | 修复缓冲、干净环境复现、演示、面试表达 | 不再首次端到端集成，不追加 P1 |

这是相对开发顺序。正式冻结晚于原计划起点时，应移动日期，而不是假定过去的日任务已经完成。

## 最小验收集：以覆盖为准，不用题目数量掩盖缺口

建议 10 个端到端/集成场景族，每族可以有多个断言；不要把下面的 10 个场景族宣传为 10 条完全独立的模型能力样本。

| ID | 场景族 | 核心断言 |
|---|---|---|
| E01 | S1 旧凭证引用 | 获批后仅一次有效配置变更，原业务探测恢复，报告有来源 |
| E02 | 迷惑变更 + 主体停用 | 根据证据转交，不尝试通过配置写入绕过停用 |
| E03 | 证据缺失/矛盾 | 有界补查，无法确认即停止修复；伪造/无关证据不能通过门禁 |
| E04 | 未审批或明确拒绝 | 受限业务写入为零；允许保存拒绝决定与本地报告 |
| E05 | 计划/资源版本变化 | 旧批准不能套新参数；执行前资源变化使旧前置条件失败 |
| E06 | 两作用域越界 | 查询、证据、记忆、thread 恢复、审批都不可越界 |
| E07 | 工具内容注入 | 不能改 scope、预算或权限；无不当副作用 |
| E08 | 审批等待时退出进程 | 重启后保留原计划及审批语义；并发/重复恢复不会启动两次动作 |
| E09 | 动作边界故障 | 提交前、提交后丢响应、回执后未 checkpoint 三个注入点，以及交付重试，都不重复业务变更 |
| E10 | Memory/Skill 跨任务 | 经确认经验被新任务读取；失效/撤销/版本冲突不被当当前事实；只加载所选 Skill 版本 |

工具超时、参数错误、Schema 失败、作用域过滤、原始证据缺失等确定性检查与上述场景复用数据，不必每次调用模型。至少 E01/E02/E03 做真实模型调查演示，其余控制路径可用脚本化模型降低回归成本，报告中分别标注。

冻结 fixture 和版本有助于复现环境，但不能承诺外部 LLM 每次输出完全一致。小样本 A/B 保持相同初始业务与记忆状态，保留原始轨迹；有余量时重复关键场景，否则明确标注单次探索结果。禁止把同一测试的经验写入后续测试，形成虚假的 Memory 增益。

## 从面试官角度：保留哪些深度

| 值得深入问的点 | 面试中应拿出的证据 |
|---|---|
| 相同 401，为什么走不同路径 | 正例/停用负例的查询轨迹、支持/反对证据、门禁结果 |
| 批准之后为什么还要检查版本 | 审批期间配置变化导致执行被拒的演示 |
| Checkpoint 为什么不能保证外部副作用只发生一次 | 提交成功丢响应、恢复重放的动作台账与业务变更计数 |
| 记忆为什么有时必须被忽略 | 新配置事实覆盖旧经验、撤销后恢复任务的例子 |
| MCP 到底带来什么，不能解决什么 | 同一业务查询通过协议接入，权限仍由可信业务边界实施 |
| 简单规则是否削弱了 Agent | 模型决定调查与假设，确定性规则负责执行许可与验收；用不同轨迹证明边界 |

不建议把“调用 interrupt”“加载 SKILL.md”“配一个向量库”单独列为亮点。实际事故案例、失败注入和可解释取舍才是主要素材。该项目也不应承诺普适根因定位或生产级 AIOps 能力。
