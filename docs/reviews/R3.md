# OpsPilot v0.2：R3 一致性复核

日期：2026-10-17。对象：用户提供的 R2 逐项回复及 v0.2-candidate 全文。下文行号指本地 v0.2 文件。

**结论：有条件通过，暂不原样升版。B1、B3、B4、B5 的架构口径闭合；B2 尚需三项小范围契约补充。** 不重选业务、不增加服务、不扩大 P0，也不要求再做一轮全面架构设计。

本报告只做设计时序推演，没有业务代码可运行，不能解释为实现已通过测试。候选稿与 R2 均未修改，没有下发 Luna 或发布冻结基线。

## 1. 本轮闭合判断

| 原编号 | R3 判断 | 依据/剩余动作 |
|---|---|---|
| B1 | 设计闭合 | 同一 integration/principal/业务路径，真实凭证校验，明确唯一修复与业务断言；停用主体不修，Gold 不向在线系统暴露。 |
| B2 | 部分闭合 | 同库事务、CAS、回执优先回查、权限先于回执返回均正确；还需 F1 动作身份稳定点、F2 授权失效时序、F3 修复与交付授权/回执的衔接。 |
| B3 | 设计闭合 | 动态只读调查与确定性门禁分工清楚；预算、Evidence、失败出口已明确。下面 C1–C3 是冻结文本校正，不新增阻断机制。 |
| B4 | 设计闭合 | 本地可信身份、stdio scope、对象归属校验与 thread 恢复检查足以支撑 P0 的诚实能力边界。 |
| B5 | 设计闭合，发布迁移待办 | 唯一 P0、相对 D1、三类评测及工时已统一；实际发布 v1.0 时还要同步旧 README/TASKS/AGENTS。 |

已接受的事务核心可以保留：同一个 Domain 事务内核验可变事实、CAS 更新配置、写动作回执和消费修复授权；Graph 检查点另行推进。SQLite 的单写事务及 `BEGIN IMMEDIATE` 支持这一 P0 设计，但需要实际处理事务回滚和 BUSY，不能由关键字替代应用条件检查。[SQLite 事务文档](https://www.sqlite.org/lang_transaction.html)

## 2. B2 仍需补充的三项契约

### F1：首次发送前必须能够恢复同一个动作身份与请求内容

**位置：** §3.2 ActionRequest/ActionLedger（127–135），§4.2 请求创建（223），恢复矩阵（254–255），单执行者（264）。

**已经解决：** 文稿明确要求重放同 key/digest，不允许恢复时产生新动作身份。

**还缺：** 动作 ID、幂等键和规范化请求是在何时、由谁固定的，首次外发前哪里可以重新取得。仅在动作成功后的 Ledger 或下一份 Graph checkpoint 中保留还不够。单执行者防止同时运行，不保证串行重启前后使用相同 ID。

**具体时序：**

1. Graph 仅保存了 Plan，执行节点临时生成 `K1/A1`。
2. Domain 使用 K1 提交成功，配置 7→8。
3. 响应丢失，Agent 在保存 K1 前退出。
4. 节点恢复后重新生成 `K2/A2`，查不到 K1 回执，再用 expected_version=7 提交。
5. CAS 可阻止第二次修改，但系统只能看到版本冲突，不能按原动作取得回执并正确续行。E09 的“恢复成功”因此仍可能失败。

这里不声称 CAS 已失效；问题是恢复关联丢失，不能由“未重复写”代替“正确恢复”。

**最小修订：**

- 为同一 `(tenant_id, task_id, plan_hash, action_kind)` 建立唯一动作意图；P0 的 action_kind 固定为 REPAIR、DELIVER。
- action_id/key 可以确定性生成，也可以由 Domain `get_or_create_action_intent` 持久登记；无需指定某种 UUID 算法，但首次业务调用前必须能重取完全相同的身份与请求。
- 规范化 digest 由可信程序计算；包括目标、环境、计划、授权和业务参数，不含每次尝试的时间戳、网络 request ID 等易变字段。Domain 重新计算并核对，不能只信客户端传入的 digest。
- Ledger 保存可重放的结果或稳定的持久结果引用；当前 Schema 只有 `result_digest`，而伪代码返回 `stored_result`，需补齐对应字段/引用。哈希本身无法还原回执。
- 同一个业务动作的网络 attempt_id 可变化，action_id/key/digest 不变。

**验收增补 E09：** 特意在“Domain 已提交，但 Agent 尚未持久保存任何本次回执”时杀进程；新进程由持久意图恢复原身份，取得原回执并完成验证。另测相同身份不同业务参数被拒。

### F2：计划替换、取消与执行需要同一个权威失效判定

**位置：** TaskBinding.status 与当前 Plan 所有权（84–98），Approval（122–125），Plan 替换（153、216），事务授权检查（226–235）。

**已经解决：** 资源/主体/认证策略版本发生变化时，旧计划不能执行；请求不能把新参数塞进旧批准。

**还缺：** 资源没有变化，但原计划被替换、其执行资格被取消时，旧请求是否仍然有效。当前 Domain 伪代码只检查原 Approval、原 Plan 和资源版本，没有明确检查“这份计划现在仍获准新执行”。TaskBinding.status 与 Graph TaskStatus 的关系也没有定义。

**具体时序：**

1. P1/A1 已获批准，资源版本仍为 7。
2. 用户在执行前取消，或用 P2 替换 P1；Graph 更新当前计划/状态，资源本身没有变化。
3. 延迟请求携带 P1 原参数到达 Domain。旧批准、快照、参数和资源版本全部匹配。
4. 若只执行现有 assert，它仍可能产生业务变更。资源 CAS 无法识别这种授权状态变化。

**最小修订：**

- 复用 Domain 的计划审批快照，增加新执行资格，例如 `ACTIVE / SUPERSEDED / CANCELLED`，或等价的 active_plan_hash/授权代数；它只管动作授权，不另造一套业务工作流状态机。
- 计划替换/执行前取消与新动作提交，在同一个 Domain 数据库中串行裁决。新动作在事务内检查原计划仍有资格、批准仍有效、当前调用者仍被授权；Graph 仅引用结果。
- 明确顺序：取消/替换先提交，尚未提交的旧动作必须拒绝；动作先提交，取消不能宣称撤销已有副作用，必须回查并报告已发生结果。
- 已提交动作的合法查询/重放继续返回历史回执，不能因为当前计划已失效就丢失历史结果；此路径仍先检查当前读取权限，且不产生新副作用。
- 审批身份、提交者身份、执行服务身份分别命名。`approver-a` 与 `support-a` 本来就不同，不能把伪代码中的 `actor` 误实现成二者必须相等。
- P0 不必增加复杂时间到期机制。如果不实现 `expires_at`，文档应称“资源版本变化/计划撤销导致失效”，不能声称已支持按时间到期的审批。

若 P0 决定不开放批准后的编辑/取消，也可以明确拒绝这些操作，禁止 Graph 单方面宣称成功；此时不能展示或承诺这些取消语义。不能一边展示 CANCELLED，一边保留原批准可执行。

**验收增补 E05/E08：** 不修改配置，先取消/替换计划，再送达原动作；业务修改为零。反向顺序先提交动作再取消，回执和已发生的变更仍可见，不返回“无副作用”。

### F3：修复和工单交付需要分别消费授权，并固定报告与验证回执

**位置：** Plan 的交付字段（114–120），Approval 单一 consumed 字段（122–125），修复事务消费批准（241），工单交付（259–262）。

**已经解决：** 工单写入被认定为受限业务写，获批 Plan 约束工单目标与字段；交付失败不能重跑修复。这一补强应保留。

**还缺：** 一个 Approval 如何授权两个独立动作，修复已消费后交付是否仍可执行，以及交付重试到底绑定哪一份不可变报告。当前只给了一个 `consumed_by_action_id`；交付策略有文字说明，但缺少可区分的消费条件。

**具体失败路径：**

- 修复把 config_version 从 7 改为 8，并标记 Approval consumed。若 Deliver 复用“批准未消费 + 资源仍为版本 7”的检查，它会在正常成功后被永久拒绝。
- 如果为避免拒绝而把 Deliver 的批准/版本检查整体放宽，又没有绑定具体修复与验证结果，仅凭同租户、同工单、允许字段不足以保证写入的是本次处置的可信报告。
- 首次交付成功但响应丢失，恢复时重新生成 report_version 或 report_ref，原去重键会改变，可能追加第二条处置记录。

这些是当前契约允许出现的冲突实现，不是声称代码已经存在上述故障。

**最小修订：**

1. 同一不可变 Plan 中明确两个操作许可：REPAIR 与 DELIVER。使用独立消费字段、唯一 ActionLedger 记录或固定两项授权子记录均可，不需要通用权限引擎。消费 REPAIR 不消费 DELIVER。
2. REPAIR 检查执行前资源版本；DELIVER 检查同一任务/计划的修复 COMMITTED 回执、在线验证回执、指定工单和允许字段。不能再要求修复前版本仍未变化。
3. 验证回执持久记录 task、plan、repair_action、实际主体/路由、观测版本、时间与业务断言结果。报告的 RECOVERED 状态来自该回执，不来自模型自由填写。它证明的是该时间点的业务恢复，不承诺服务此后一直健康。
4. 首次发送 Deliver 前固定 `report_ref/report_version/content_digest/verification_ref`。允许通过 `(task, plan, repair_action)` get-or-create；崩溃重放使用原版本和原内容。
5. 去重记录与工单写回在同一事务内提交；相同交付身份配不同 payload_digest 拒绝。P0 一份最终报告即可，修订报告作为显式新操作处理，不得由自动恢复偷偷生成。
6. Plan 无需预知尚未生成的报告正文。它可以授权“从本任务的权威修复/验证回执构造指定字段的最终报告”；Domain 核对报告来源、任务/计划、目标和字段约束。报告生成后才计算交付请求 digest。
7. 首周优先追加本任务的处置记录，避免覆盖人工维护的工单字段；若要覆盖全局工单状态，需要相应版本条件，不能只凭字段名在允许列表中就覆盖更新。
8. 未提交的交付仍检查当前执行资格/读取权限；修复曾成功不意味着获得不可撤销的任意写入许可。已提交交付可以合法回查历史结果。拒绝审批分支仍仅输出本地报告。

**验收增补 E09：** 修复消费授权后，正常 Deliver 仍能成功；Deliver 成功丢响应后重启仅一条记录；同一交付身份不同报告内容拒绝；另一个任务/租户的报告或验证回执不能用于本任务交付。

## 3. 可在冻结时直接校正的说明，不增加新阻断项

**C1：统一预算强度和时间口径。** §3.1 的调用台账写“如果启用”，§3.3 又写持久预留，应明确 P0 是否启用。建议按每次真实出站 attempt 预留计数，失败/重试也计数；保守扣减但未发出可以少用一次，不允许反复重放同一预留记录免费发请求。调查活跃时限、单次调用超时与人工审批等待分开，避免隔天审批恢复时被短调查超时直接终止。模型调用次数上限可硬控，token 成本仍按可获得用量报告。

**C2：补齐控制路由的命名。** `UNKNOWN` 是客户端尚不能确认动作结果，不需要强塞进 COMMITTED Ledger；使用 `WAITING_INPUT + blocked_reason=ACTION_OUTCOME_UNKNOWN` 或一个明确等价状态。READY/NO_ACTION/INCONCLUSIVE 之外的控制层 DENY 和 WAITING_INPUT 不要偷偷加入四值 Gate 枚举。E04 应检查配置及未经授权工单写入为零，而不仅配置为零。

**C3：恢复时检查撤销状态，也检查当前上下文缓存。** Memory 在任务挂起后撤销，恢复时即使 checkpoint 里仍带着旧片段，也不能直接再次送给模型；按资产 ID/版本重新装配或去除失效内容。Gate 校验已有证据，若额外查询实时状态，记录并纳入相应调用口径；不要通过 Gate 自动查齐所有事实后仍把它宣传成模型动态调查。

**C4：明确事务边界和版本更新纪律。** principal/auth_policy/config 的可变授权事实应在同一 Domain 数据库事务内读取；所有相应业务变更递增版本，P0 运行时不复用旧版本号。不要在 `BEGIN IMMEDIATE` 写事务中等待模型、MCP、HTTP 或人工批准；业务探测在事务外执行并保存其观测版本。事务提交失败或 BUSY 按明确策略退出/重试，不回传虚假的成功。

**C5：发布迁移，不另开设计议题。** 当前目录中的 README/TASKS/AGENTS 仍是旧工单方案和两个 Skill 口径。发布 v1.0 时一起同步；R2 的人类可读参考文件名与实际乱码文件名不同，也应修为有效链接。D1 中 `credential sidecar` 建议明确为工具侧本地凭证模块，无须为了这个词新增独立服务。本轮没有核验或修改自动提醒的后台状态。

## 4. 供主 Agent 直接纳入冻结版的最小补充清单

以下内容只补现有合同，不要求额外平台或再次扩展场景：

1. 明确 REPAIR/DELIVER 的动作身份在首次外发前可恢复，固定 request digest，Ledger 有完整回执或持久引用。
2. 明确 Domain 对当前计划执行资格的权威记录，以及取消/替换与提交的串行顺序；若 P0 不提供对应功能，明确拒绝且不宣称取消成功。
3. 分开 REPAIR/DELIVER 的授权消费；固定验证回执和报告身份，交付写入与去重同事务。
4. 将本报告新增时序并入现有 E05、E08、E09，不增加一个新的测试平台或新业务场景。
5. 合并 C1–C5 的文字校正，发布时统一实施入口。

**放行标准：** F1–F3 写入同一份候选/冻结合同后即可做针对性核对；本轮不要求再全面评审选题、框架、目录或所有模块。其他 B 项不重新打开。不能在这些条款仍未决时直接回复“五项全部闭合”。

| 待回复 ID | 只需要回答的决策 |
|---|---|
| F1 | 动作身份确定性生成还是持久 get-or-create；首次发送前的固定点在哪里；回执如何重取 |
| F2 | Domain 怎样判断旧计划不可再执行；取消/替换与已提交动作如何分界 |
| F3 | 两项授权如何独立消费；报告/验证回执怎样固定并用于幂等交付 |

以上是继续收敛 B2 的三项局部修改，不是重新否定已经接受的事务架构。补齐后，我支持升级为唯一实施基线并按原定相对 D1 顺序推进；架构放行与未来代码/运行验收仍然分别进行。
