| 项目 | 结论 | v0.3 依据 | 为什么足够开工 |

### F1：原先的恢复缺口已经消除

现在的因果顺序是：持久 Intent → 发送动作 → Domain 提交业务变更和 Ledger → Graph 推进。无论崩溃发生在 Intent 返回前、业务提交后响应返回前，还是 Graph 保存回执前，都可以从 Domain 找回原动作身份。

首次创建与历史读取的权限条件也已经分开：尚未提交的动作需要重新核验当前执行资格；已提交的动作在当前读取权限允许时只返回历史结果。意图持久化没有变成永久授权。

`result_json_or_ref` 补齐了原稿中只有摘要却需要重放完整结果的缺口。实现采用数据库内完整 JSON 或稳定持久引用均可，引用必须确实可恢复。

### F2：资源版本之外的授权变化已有裁决点

旧批准与资源版本保持不变，不再意味着旧计划可以继续产生副作用。Domain 在真正提交前读取当前 Plan 资格及分项许可；Graph 的 CANCELLED 只是结果投影。

两种顺序均有定义：

- 取消/替换先提交：旧计划不能新提交 REPAIR，也不能新提交 DELIVER。
- 动作先提交：保留动作及其回执；之后的取消只能禁止未提交动作，不能把已有结果改写成“从未执行”。

审批者、发起者、执行服务的身份也已分开，避免把“当前执行者”错误等同于“批准人”。这些足以指导本地 P0 实现，不需要再增加分布式协调或复杂 IAM。

### F3：正常交付与重试交付已有一致路径

REPAIR 消费自己的许可，DELIVER 保留独立许可。交付校验绑定同任务、同计划的修复与验证回执，不再要求修复前的配置版本继续存在。

报告在 DELIVER 首次调用前持久冻结，恢复时查回原报告、原 Intent 和原交付回执。工单追加与去重记录同事务，解决了“已经写入但响应丢失”后再次追加的风险。恢复失败、未批准或无交付资格则走本地报告，不偷偷写工单。

验证结果被准确限定为某个观测时刻的真实业务恢复，没有承诺此后服务永久健康。P0 的这项边界合理。

## 3. 将既有契约带入代码验收，不新增设计前置条件

以下是 D3/D4 应从 v0.3 落到代码和 E05/E08/E09 的检查点，主 Agent 可以直接编入开发任务；无需先回复本评审或再提交一版设计。

| 验收关注点 | 最小断言 |
|---|---|
| Intent 响应也可能丢失 | 登记已提交但调用方未收到结果，重试仍只有一个 Intent，返回同一身份与 canonical request。 |
| REPAIR 提交后丢响应 | 同一动作回执可恢复；配置版本只增加一次；根据回执继续验证。 |
| 取消/替换的正反顺序 | 资格先失效则无新副作用；动作先提交则历史可查。分别覆盖 REPAIR 与 DELIVER。 |
| 生命周期命令重复或延迟到达 | 重复审批不得重置已消费许可；旧 activate/approve 请求不得把已取消或替换的同一计划重新激活。显式新计划和新审批按既定流程处理。 |
| 历史读取与新执行权限分离 | 执行资格已撤销但读取权限仍在时，可取历史回执；这条读取路径不得产生新写入。 |
| 报告冻结后进程退出 | 恢复先查已有 Report/Intent/Ledger，不因重跑模型生成不同正文、验证引用或 report_version；显式冲突按契约拒绝。 |
| DELIVER 提交后丢响应 | 回查原交付回执，工单处置记录仍为一条，REPAIR 不再执行。 |
| 交付内容或归属被替换 | 同身份异内容拒绝；跨 task/tenant 的报告、修复回执或验证回执不能交付。 |
| 权限消费与业务写入原子性 | 同事务提交配置/工单、回执和相应消费状态；失败无部分业务写入。 |

这些断言验证的就是当前承诺，而不是新增审批功能、场景或平台。特别是“旧 activate 不复活旧授权”和“恢复先读固定报告”，属于实现既有失效/冻结语义的必要编码顺序。

逻辑 Schema 和伪代码尚不是 DDL 或可执行程序：`action_intent_id` 可以映射为已有 action_id 或独立主键，重要的是唯一定位同一持久意图并核对归属；具体索引、外键、异常映射与事务清理在实施时落实即可，不需在架构阶段逐一指定。

框架和数据库也不能代替这组业务断言。LangGraph 官方说明恢复会从包含 interrupt 的节点开头重新执行，因此副作用与资产恢复需要代码正确处理。[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

SQLite 的单写事务和 BEGIN IMMEDIATE 支撑当前同库裁决方案，但仍要正确处理 BUSY、失败回滚与事务结束；这些列入代码验收，不作为继续延迟开工的理由。[SQLite Transactions](https://www.sqlite.org/lang_transaction.html)
