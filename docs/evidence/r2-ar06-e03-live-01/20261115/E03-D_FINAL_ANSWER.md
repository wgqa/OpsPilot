## 二、实质差异（唯一一处，但语义变化不小）

**v1 的判定方式（宽松、按状态码+错误码）**
> 503 响应且错误码为 `TEMPORARY_UNAVAILABLE` 即视为可重试；`SCHEDULED` + 可信 `retry_at` 表示发送方还会再试，应等待该次尝试而不要并行重发；只有达到尝试上限且可信状态为 `EXHAUSTED` 时才联系回调运营方；关联 response request、event、order 与 attempt count。

**v2 的判定方式（严格、需多重证据一致）**
> 503 只有在服务端记录了可重试的失败码**且**存在当前重试策略时才可重试；`SCHEDULED` + `retry_at` 仍表示待处理；`EXHAUSTED` 只有在 `attempt_count` 达到 `max_attempts`，**并且**失败响应摘要、event、request 三者都与当前投递行匹配时才可采取行动；文档本身只描述方法，具体事件由当前 Domain 证据判定。

关键变化归纳：
1. **可重试性从"看响应"变为"看服务端记录"**：v1 客户端凭 503 + `TEMPORARY_UNAVAILABLE` 就能自行决定重试；v2 要求服务端已记录 retryable 失败码和当前重试策略，客户端不能仅凭响应码推断。
2. **新增显式计数参数**：`attempt_count` 与 `max_attempts` 成为判定"耗尽"的必要条件（比较工具将其标为候选词法线索，属调查提示，不等于运行时已采用）。
3. **耗尽判定要求三方一致性**：失败响应摘要（digest）、event、request 必须与当前投递行匹配，否则不能认定 EXHAUSTED。
4. **职责边界更明确**：v2 明确"文档只描述方法，当前 Domain 证据决定事件"，即协议不再充当状态事实来源。

## 三、配置影响（需研发/运维逐项核对，非已确认事实）

- **重试策略配置**：v2 依赖"当前重试策略"存在。若线上没有显式配置策略（或策略为空/过期），503 将不再自动可重试——这是最容易踩的坑。
- **计数与上限字段**：需确认投递记录中 `attempt_count`、`max_attempts` 是否被真实写入并随每次尝试递增；缺失时 EXHAUSTED 永远无法成立，告警会静默失效。
- **失败码映射表**：v1 的 `TEMPORARY_UNAVAILABLE` 单码判断需扩展为"可重试失败码集合"，需核对网关/回调服务端的错误码分类配置。
- **摘要与关联字段**：需确认失败响应 digest、event_id、request_id 与投递行（delivery row）的关联键在存储层可查且一致，否则一致性校验会误判。
- **项目配置版本**：知识检索显示该项目配置的契约版本为 2、最新可用版本为 2（`configured_contract_version=2`，`deployment_version_verified=false`）。这只能说明**项目配置/文档范围**指向 v2，**不能证明线上已部署 v2**。

## 四、兼容风险

1. **行为收紧导致"该重试的不重试"**：依赖 v1 宽松语义的调用方，在 v2 下若服务端未记录策略，会把可恢复的 503 当作终态，造成回调丢失。
2. **重复投递风险反向变化**：v1 强调"等待 retry_at、不要并行重发"；v2 增加一致性校验，若调用方仍按旧逻辑自行重发，可能与服务端调度叠加，产生重复处理。
3. **告警/工单触发条件变化**：v1 只需 EXHAUSTED；v2 需 attempt_count==max_attempts 且三方匹配。旧监控规则可能漏报或误报。
4. **混合版本期**：v1 与 v2 文档均自 2026-10-01 起有效，若发送端与接收端/消费端版本不一致，判定口径会分叉。
5. **文档不能覆盖的未知**：网关路由行为、未公布的运行时修复、消费者实际适配情况均未验证。
