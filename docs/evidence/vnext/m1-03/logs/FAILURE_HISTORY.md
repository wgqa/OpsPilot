# Browser smoke failure history

These entries record observed failed runs without treating them as passes. Attempts 01 and 02 were written to the same `browser-full.txt` path before the smoke harness rotated logs; their raw browser logs were overwritten. The error details below are from the captured command results, not reconstructed raw logs.

- Attempt 01: login rejected with `ORIGIN_REJECTED`; the server launcher had ignored the configured Vue Origin and expected the API's own port.
- Attempt 02: the real S1 Task reached `WAITING_APPROVAL` and persisted four successful MCP observations, but the inspector returned no Evidence because its read query expected `SUCCEEDED` while the Domain stores successful observations as `OK`.
- Attempt 03: the Task and Evidence were visible; the browser acceptance check found that the APPROVER page still rendered a disabled SUPPORT-only “create S1 investigation” button.

Attempt 03's sanitized raw browser log and failure result are preserved beside this file. The smoke harness now creates a numbered log for each subsequent browser attempt so later retries do not overwrite it.
- Attempt 04: the full browser scenario passed, including 3 real Provider turns, a refresh while the third answer was still RUNNING, four MCP Evidence cards, and the SUPPORT/APPROVER and cross-tenant checks. The top-level smoke then failed before restart validation because the browser record used `taskId` while the Python runner expected `task_id`. The sanitized browser log and partial machine result are preserved; the key name is now consistent.
- Run 20261018T070756Z: the complete Microsoft Edge scenario passed, including UI mappings for 401/403/409/network timeout, mid-stream refresh, the real S1 Evidence answer and API restart. All five real Provider turns returned token usage, but the locked LangChain streaming metadata omitted the response ID. This is recorded as a trace gap, not as a Provider-ID pass; the server now opts into response headers and records only the provider request/correlation ID for the next independently fresh run.
- Run 20261018T071119Z: the complete real-browser scenario, API process restart, four UI error mappings, and all five real Provider answers passed. `REAL_PROVIDER_CORRELATION_IDS` failed because the selected Provider's streaming response did not yield an ID in the metadata fields we currently inspect. The attempt is preserved with `status: FAIL` so no response-ID capability is claimed; the next run adds key-name-only runtime diagnostics to identify the Provider's documented correlation header.
- Run 20261018T071319Z: repeated the full browser and restart flow with `include_response_headers=True`; all cases except Provider IDs passed. The diagnostic used the default logger and did not appear in the captured service log, so that run adds no response-header-key evidence. Its FAIL result is retained. The next smoke enables opt-in stdout diagnostics containing header names only.
- Run 20261018T071503Z: the real Provider response metadata contains `x-ds-trace-id` in response headers; the attempt remained FAIL because the extractor did not yet recognize this provider-specific correlation header. Logs preserve only header names, never header values. The next run adds this exact header to the identifier allowlist and must prove persisted IDs before the check can pass.
