# C2 发现的两跳来源传播：修改前冻结 RED

源码嫌疑：`_prepare_context`会保留仍有效的助手历史，但按预算移除低优先级直接Memory块；新回答持久化`MODEL_ATTEMPT`祖先引用。`_message_source_valid`对该引用目前只检查旧模型调用状态与响应ID，不递归校验该调用生成的助手来源。因此祖先Memory撤销可能通过预算裁剪后的派生回答继续进入新Context。

先新增两项定向回归，分别用现有EPISODIC与SEMANTIC合法来源：第1次确定性助手依赖ACTIVE资产；第2次使用正常低预算，确认直接Memory块被排除、第一条助手仍实际选入，提交派生回答；撤销资产；第3次在足够预算下，必须同时排除直接及派生助手，Manifest给出来源失效原因。撤销前同链应仍有效。确定性模型完成是测试替身，不计真实Provider/MCP。

若RED确认，只在既有来源验证中补MODEL_ATTEMPT→所属AssistantMessage的递归、同Tenant/Session/Task校验和环保护/复用，兼容旧持久行，不改Schema、业务状态、Gate、审批或动作事务。新鲜GREEN、原完整回归必须通过。

原B实验8轮和失败摘要不重写。本问题若确认属于本卡允许的直接P1 Context正确性修复。修复后允许且仅允许一次独立的有界真实GREEN旅程：以现有Task D在新的正常审批后取得v11→v12真实结果作为新来源，新Episodic与不同目标Task，显式fixture v12→v13。使用同一B_INPUTS和3600输入预算、SDK0重试、每Run原3次、ACTIVE最多8轮、撤销后2轮。通过正常认证Web API连续提交，真实浏览器查看；与第一次B目录/ID分开，不增加原8轮。该旅程同时检查被预算裁掉直接Memory后的派生助手和目标Summary撤销，所有失败留存；不得再开第三个摘要实验追求通过。

下一次真实GREEN前另存准确来源/目标/Memory/输入摘要，代码变化及阶段边界。仅在RED确认后实施，不修改冻结合同，也不提前开发其他功能。
