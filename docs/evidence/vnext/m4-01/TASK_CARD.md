# OpsPilot｜M4-01 对话驱动调查任务卡

**基线：** `main@90c80fd`
**目标：** 让用户通过自然语言纠错，经过确认后真正更新 Task 并重新调查，而不仅是获得聊天回答。

## 一、实现范围

1. **自然语言意图识别**
   - 区分普通追问、关键纠错和假设讨论。
   - 模型输出结构化的调查更新提议，附原消息、目标 Task、版本与变更摘要。
   - 不建设通用意图路由平台。
2. **受控确认与调查恢复**
   - Web 展示更新前后差异，由用户确认或取消。
   - 确认时校验提议版本、身份、任务状态及幂等键。
   - 复用现有 `CORRECT_TASK_INPUT` 和 TaskControl，不重写旧状态机。
   - 受理后阻断旧 Run/Plan，由新 Run 重新获取可信 Evidence，并向用户解释判断变化。
   - 重复确认不得创建重复 Run；过期提议必须拒绝。
3. **真实业务验证**
   - 用户改口但事实不变：真实 Probe 仍为 401，不能迎合用户判断。
   - 用户改口且事实变化：受控环境独立准备真实 403，再调查匹配 Request ID 的授权事实。
   - 测试准备动作与 Agent 自身行为分别记录。
   - 不能通过聊天绕过 TaskBinding、审批或业务权限。

## 二、验收标准

冻结测试后再开发，至少覆盖：

- 普通追问只解释，不重启调查。
- 关键纠错提出更新，确认后实际重新调查。
- 假设性表达不触发正式纠错。
- 重复确认不产生重复任务。
- 任务版本变化使旧提议失效。
- 401/403 的两组成对事实实验。
- 页面刷新、服务重启后可查看真实任务状态。

提供真实 Web、Provider、MCP、TaskControl、Evidence 与最终结果的关联 Trace。

## 三、开发边界

- 不合并 Chat 和 Investigator Runtime。
- 不新增业务场景、Memory 类型或 MCP 工具。
- 不改变原 S1/S2 Gate、审批及事务安全语义。
- 不直接开放用户修改可信 TaskBinding 资源。
- 原合同 M4 总验收保留，并记录阶段命名变更。
- 上一阶段遗留安全门禁如阻塞本轮，先报告和处理；不得绕过。

## 四、交付

提交源码、RED/GREEN、完整回归、真实用户旅程、失败记录，以及源码学习与面试材料。

**本阶段必须回答：**

- 用户相比以前多完成了什么？
- 模型实际决定了什么？
- 哪些行为仍由可信程序控制？
- 哪些结果由真实证据证明？

完成后提交 SHA，停止等待主 Agent 独立验收，不自行进入 M4-02。
