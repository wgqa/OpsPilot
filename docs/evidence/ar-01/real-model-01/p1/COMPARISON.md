## 模型行为与程序行为分开看

- **材料题**：B 自主选择无需工具是合理决策。原始模型返回解释 + `<result>{...}</result>`；既有共享解析器只接收裸 JSON、特定 fenced/前缀形式，返回 None 后由程序生成 `UNSUPPORTED_OR_EMPTY_ANSWER` 的 PARTIAL。Fallback 反而讨论当前事件缺口，与纯解释目标不符。归因是输出契约遵循/交付接口不匹配；不据此判定标准 Loop 不会解释。没有修解析器、重试或替换答案。
- **202/503 成对观察**：问题正文相同，数据库事实不同。202 时两组继续看 Receiver 并明确 QUEUED≠PROCESSED；503 时 A 以投递与不完整历史交付临时失败/待重试，B 继续找 Receiver 与重试知识。说明新观察进入了不同合法后续选择和结论，而非根据用户断言决定事实。所列顺序仅为实际轨迹，不是新规则。
- **Event 身份**：E1 的真实历史 503 与 E2 的当前 PROCESSED 不能组成 E1 恢复证据。两组都承认 E1 当前处理未知；现有 Receiver 工具只给当前关联事件，无法凭这一工具取得任意历史事件的当前 Receiver。这是工具事实能力边界，不能靠模型补全。
- **混合目标**：A 的真实出站 Context 明确含“再查本订单当前状态”，六种工具也在场，没有预算/授权拒绝；模型主动提前结束。B 提议越域历史读取后受信 MCP 返回 `S3_EVENT_NOT_AVAILABLE_WITHIN_BOUND_ORDER`，随后仍完成合法部分。一次被拒提议是成本与策略现象，不是越域事实已泄漏。
- **细节局限**：A failed 把“本轮未查 Receiver”写成“没有接收方处理状态记录”，缺少对未观察与不存在的区分；A scope 有易被理解为笼统禁止跨 Event 的措辞，实际同订单跨 Event 查询仍合法。B acknowledged 有“不是因为存在反面证据”的不当句子；202 明明反对“投递失败”假设。主结论正确不应掩盖这些质量问题。
- 六工具中实际使用五种；两组均未调用 `load_callback_skill`。Knowledge 使用 A=1、B=1，没有 Memory/Skill 增益或跨 Run 连续体验的效果证明。可观察的是工具选择、结果及可见解释，不能凭序列推测模型未公开的内在推理。
