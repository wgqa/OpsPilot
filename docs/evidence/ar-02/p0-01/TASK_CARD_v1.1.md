## 1. 唯一用户目标

用户不必选择故障类型，也不必先创建业务 Task，即可开始一次专业技术支持对话。

助手能够根据目标自主决定直接解释、分析用户提供的材料、查询授权 Knowledge、请求合法业务调查、根据 Observation 继续查询或停止，并把结果带回原会话。

P0 必须同时完成**统一入口和基本连续性**。不允许先交付一个只能单轮调用工具的入口，再把会话历史、纠错和恢复留给 P1。

## 2. 本轮迁移范围

**新增交付范围：**

自然问答／粘贴材料 → 授权 Knowledge → 已有业务范围内的只读 MCP 调查 → 原会话解释或交接说明草稿。

**保留但不要求迁移的范围：**

既有 S1 获批修复、S2 正式诊断及交接提交、S3 受控交接路径继续按原 Domain 机制运行，执行必要的兼容与安全回归。本轮不要求在新 Loop 中重建这些业务动作。

本轮可以优先使用 S3 订单与异步回调数据证明端到端调查，但通用 Chat、材料处理和 Knowledge 不得实现成一个只识别 HTTP 202 的专用 Router 或 Workflow。

### 决策核心与工具粒度

- 以 `create_agent` 自由循环作为新的产品决策核心候选，采用渐进迁移。
- 模型可以直接选择合法的原子只读能力：订单、投递、Receiver、历史记录、Knowledge 等。
- 正式修复、受控提交和业务回执由原有可信 Domain 及必要的专业执行协议负责。
- 旧 Investigator 作为未迁移业务的过渡路径和对照基线保留，不要求新能力双份实现。
- 单个 Run 使用固定的执行核心及其恢复机制；不开发跨核心 Checkpoint 热切换。
- 不新增 Supervisor、多 Agent 平台或强制目标清单。

## 3. 无业务 Task 的 Knowledge 访问合同

这是 P0 必须明确实现的边界，不能仅以“需要授权”概括。

### 3.1 可信身份和访问范围从哪里来

复用现有 Web 登录所形成的服务端可信身份，包括 tenant、actor、role 和 Session owner 校验。

对于尚无 Task 的资料访问，提供一份**本地 Demo 的小规模服务端可信资料范围映射**，把已认证身份关联到允许读取的项目或文档集合。

实施方先检查现有可信资源目录和访问记录能否复用；缺少对应关系时，可以增加最小服务端配置或绑定记录，但不引入完整 IAM、权限平台、伪造故障 Task 或模型控制的项目授权。

本地 Demo 若只有一个授权项目，可自动使用该项目；若有多个授权项目，可向用户展示服务端过滤后的可选项目。

### 3.2 选择和复用规则

- 当前 Session 已有合法资料范围：直接检索，不重复询问。
- 尚无选择但只有一个允许范围：自动使用。
- 存在多个允许范围且问题无法判明目标：请用户选择。
- 用户更换项目：重新按服务端授权集合检查，再更新 Session 中的工作范围。
- 无授权范围：拒绝受保护资料读取，但允许不依赖该资料的普通概念问答。
- 每次实际读取仍校验身份、资料范围、来源版本和当前访问资格；不能只依赖早先选择或模型历史文本。

用户、Prompt 或工具参数里的 `project_id`、`service_id` 和项目名称只能作为选择线索，不能直接产生授权。

### 3.3 适用版本与最新版的区别

Knowledge 查询需区分：

- 用户声明的版本或检索偏好；
- 当前受信项目配置所证明的版本；
- 资料库中的最新版本；
- 当前问题实际适用的版本。

例如，用户说“我们使用 v2.0”，可以按 v2.0 查找，但该声明本身不证明线上确实部署了 v2.0。若当前可信配置或请求事实显示其他版本，应说明冲突。

禁止把“优先最新文档”写成固定策略，也禁止让旧文档覆盖当前可信业务事实。

## 4. P0 基本 Work Context 与恢复

优先复用现有 Session、Message、Run、Chat Context、消息来源关联、SSE 及 Worker。除非证明现有结构无法承载，不新增独立 Goal 数据库、任务计划引擎或通用 Context 平台。

模型本轮所需信息包括：

- 原始目标和最近交互；
- 用户粘贴的相关材料；
- 已取得的工具结果与来源；
- 本 Session 中仍待解答的问题；
- 已确认更正及被其影响的旧依据；
- 当前 Task/Run 的可信业务状态与事实形成时间。

这是一套可重建的工作上下文，不是新的业务事实权威。

**恢复至少覆盖两类情况：**

**R1：已完成一轮后重新打开。** 浏览器刷新或服务重启后，用户仍能在原 Session 继续提问，读取之前的合法材料、工具结果和来源。

**R2：调查进行中被中断。** 选择一个代表性中断点，例如工具 Observation 已持久化、最终回答尚未保存。恢复后应能继续合法执行，或明确显示中断和可恢复状态；不得无声丢弃问题、形成两条最终答复或制造重复业务副作用。

只读工具可因 TTL、身份变化或恢复需要重新取证；不以“任何 MCP 调用都不能重复”为目标。恢复时必须重新验证权限、Run 状态及必要来源。

普通更正可以直接更新对话理解；涉及订单绑定、关键业务调查输入或受控动作依据的正式纠错，继续复用 TaskControl、确认及新 Run 规则。

## 5. 首轮 Gold：行为标准，而非固定模型输出

| ID | 任务 | 必须满足 |
|---|---|---|
| G01 | 无 Task，只问 HTTP 202 含义 | 正确解释，可零工具结束 |
| G02 | 粘贴回调日志 | 根据材料解释，区分事实与推测 |
| G03 | 查询项目适用的协议 | 在可信资料范围内检索适用版本，区分最新版 |
| G04 | 查询自己的订单 | 合法绑定后自主选择只读工具，以当前 Observation 回答 |
| G05 | 概念 → 日志 → 业务调查 | 跨轮保留目标、材料和来源 |
| G06 | 更正目标 Event | 新 Event 重新核查，不借旧 Event 的成功状态 |
| G07 | 越域请求与本订单合法请求混合 | 阻断越域读取，继续可合法完成的剩余目标 |
| G08 | 仅整理既有结果 | 能直接形成来源清楚的说明，不强制重新调查 |
| G09 | 刷新及代表性运行中断 | 恢复上下文和合法执行状态，不重复最终答复或业务写入 |
| G10 | 相似问题，不同真实事实 | 结论及下一步可随 Observation 合理变化 |

G01～G10 作为完整行为 Gold 保留。阶段 A 只为关键的接口、状态和安全缺口准备确定性 RED；不强求每个 Gold 都配一个预设模型输出的 Mock。

Gold 不规定唯一工具顺序，不强制必须使用 Skill，也不强制模型调用某个固定次数。

## 6. 实施顺序：尽早让真实模型进入验证

### 阶段 A：最小差距核对与关键 RED

先制作一份简短的差距表，列出现有 `Chat / Session / Worker / SSE`、AR-01 决策循环、MCP、Knowledge、Domain 之间需要改变的接口。

只冻结关键输入/输出、可信资料范围、运行恢复和安全边界。优先复用现有代码，不开展完整架构重新选型或大型文档工程。

阶段 A 的退出条件是：最短链路的接口与代表性 Gold 已明确，可以开始写实际产品路径。

### 阶段 B：最短可用链路与早期真实模型 Smoke

先实现：

1. 普通 Session 无 Task 问答；
2. 授权 Knowledge 查询；
3. 在用户明确提供合法业务对象后进行只读调查；
4. 将工具结果和回答持久返回同一 Session；
5. 下一轮能够引用前一轮材料及调查结果。

**达到最短链路后，必须安排真实模型验证检查点，而不是等所有 G01～G10 都实现完毕才第一次调用 Provider。**

早期真实模型 Smoke 建议选择：

- S01：无 Task 的概念解释，以及模型是否能合理地零工具结束；
- S02：同一 Session 中先读适用 Knowledge，再进入获授权的 S3 只读调查，并在新的 Observation 出现后继续回答。

这两个 Smoke 验证产品入口、实际工具选择和上下文接续，不是新旧框架的胜率实验。

#### 早期付费预算提案（待单独批准）

- 模型：沿用当前可用的 `deepseek-flash` 配置，不擅自更换供应商或模型。
- 范围：S01、S02 两条冻结旅程，每条只安排一次初始执行。
- Provider：建议全局上限 **16 次请求**。
- MCP：建议全局上限 **12 次工具尝试**，同时遵守既有单 Run 限额。
- 费用：建议全局估算上限 **USD 0.20**，实际扣费另以供应商账单为准。
- 不自动重试，不扩大样本，不复用已消耗的 AR-01 付费授权。
- 首次真实请求前必须验证持久预算登记、未知用量保守处理、停止条件、模型请求及工具 Trace 的脱敏记录。若无法可靠执行总预算约束，停止付费 Smoke。

**以上仅是授权申请参数，不是授权本身。**

如果付费授权尚未取得，可以完成免费确定性接线及关键回归，但真实模型效果保持 `NOT_RUN`。不能用 Mock 绿灯替代本阶段的模型自主性证据。

若 Smoke 暴露接口、上下文或模型行动问题，先诊断根因再推进下一组能力，不要立即追加硬性 Goal Gate。

### 阶段 C：连续旅程、恢复和独立验收

在早期 Smoke 的反馈基础上补齐必要的 G01～G10 行为、一个代表性进程中断、已有安全回归和产品展示。

分别保存模型原始行动、MCP/HTTP、可信状态、用户结果、错误与停止原因。

对于实际浏览器体验，严格遵守既有工具环境限制。若 B-11 的浏览器停止条件仍未解除，相关项目继续 `HOLD / NOT_RUN`；不得用替代浏览器脚本冒充既有 Stage B 验收。

完成后提交 `ACCEPTANCE_CANDIDATE`，等待主 Agent 独立验收。

## 7. 禁止扩展与停止线

本轮不实施：

- S1 修复、S2/S3 正式交接在新 Loop 下的完整迁移；
- 新的业务写入口或自动批准机制；
- 跨会话长期 Memory 的通用化改造；
- 大规模长对话摘要和 Memory ON/OFF 收益实验；
- 双引擎热切换、Supervisor、多 Agent 平台；
- 自建通用 Tool Gateway、Goal 管理框架或 Runtime；
- 新 S4/S5 业务系统、任意 Shell 或外部企业集成。

如果当前核心能力不支持某个合法用户目标，应先判断是能力缺口、Context 缺失、输出合同问题还是模型策略问题。除安全不变量外，不得自动将失败转为运行时硬门禁。

停止条件：一条完整的自然对话—资料—合法调查—原会话交付链可复现，基本连续性和代表性恢复得到验证，关键安全不变量无退化，剩余产品缺陷、未运行项和费用可核对。

不因希望提高测试数量、增加技术组件或追求全部模型输出一致而无限扩展 P0。
