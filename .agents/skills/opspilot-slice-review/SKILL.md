# OpsPilot 切片开发与主 Agent 独立评审

## 适用范围和权威来源

本 Skill 是**工作流程入口**，不是新的产品、安全或阶段合同；不取代、更不复制一份不断漂移的北极星。权威来源依次核对：当前目标提交 `PROJECT_NORTH_STAR.md`（尤其 §0、§2、§3、§4、§6、§8）、根目录 `AGENTS.md`、本阶段冻结任务卡/Gold、相关 `DEFERRED_GATES.md`、上阶段的有效主 Agent 裁决及适用历史不可变合同。有冲突就指明具体文件/版本和冲突，不能自行选择对自己最方便的规则。

## A. 每次进入 OpsPilot 开发会话时（开发、测试、调试、提交均适用）

1. 先检查 `git status`、当前 branch、`git rev-parse HEAD` 和远端 `main` / 目标分支 SHA（远端不可读就明示，不猜测）；明确工作的 Base、HEAD 和适用 Diff，不用历史聊天中记载的 SHA 冒充当前值。
2. **实际打开并读取**当前目标提交的 `PROJECT_NORTH_STAR.md` 和根 `AGENTS.md`；记录文件 Blob SHA。读取本阶段任务卡、冻结验收合同、遗留门禁与最近有效裁决。Skill 的存在或被选中不代表上述文件已经读过。
3. 用一段短话确认项目北极星：当前任务服务哪条真实用户旅程或哪项明确学习问题？为什么不属于增加无意义状态/限制？如与北极星不符，先指出并提出最小修正。
4. 公开简短的“开工核验”：Repo / Branch / Base SHA / HEAD SHA / 总纲 Blob / AGENTS Blob / 冻结合同 / 证据缺口。**没有实际核验的项目填 UNVERIFIED。**
5. 只执行当前批准切片；每轮普通代码修改不重复长表。阶段范围改变则转 B，正式验收则转 C。

## B. 仅当**正式规划、范围变更、设计裁决**时

每项以 1—2 句话回答六问：

1. **用户变化**：前后哪个用户任务可以完成？安全修复和学习实验如实标注。
2. **Agent 决策**：模型能真正决定查询、澄清、Knowledge/Skill/Memory 使用、继续或结束的什么内容？程序仅守住可信边界；没有自主性提升时直说。
3. **观察驱动**：给一组成对观察及不同合理动作；不要写死唯一工具序列；纯修复可说明不适用。
4. **约束双向检查**：每项新硬限制具体保护什么不变量？必须挡住什么风险、必须保留什么合法行为，各由哪些正反证据证明？
5. **责任归属和简化**：这是新风险还是共同职责的重复问题？落在哪个现有模块？具体哪些旧条件能够删除、合并或软化？未经证据不得声称已删除。
6. **证据与停止线**：冻结哪些旅程、Gold、Trace、真实 HTTP/MCP/Provider、成本与失败；何时停止本切片？不可用测试数量冒充产品结果。

另检查：本次是否又把 Agent 变成固定 Workflow；是否把管理方便升级为硬性 Gate；若连续多个切片只有治理没有可演示用户变化，下一轮优先纠正产品能力，但真实安全问题仍处理。

## C. 每次正式代码审查或阶段验收时

### 前置核验区块（必须在结论之前）

- Repo / Branch / Base SHA / Candidate HEAD SHA；Diff 范围、是否包含合并与治理文件变更。
- `PROJECT_NORTH_STAR.md`：实际阅读状态、目标版本和 Blob；`AGENTS.md` 同样记录。
- 冻结合同、任务卡、遗留门禁及其版本/优先级；历史 Gold、RED、失败不可重写。
- 实际源码/测试/Trace/HTTP/MCP/Provider/浏览器检查范围；区分**实施方报告**、**保存日志的独立审阅**、**源码与原始 Trace 的独立核验**、**本人亲自复跑**。未做的标 `NOT_RUN`。
- 关键基线、合同或必要证据缺失时 `HOLD/UNVERIFIED`；不能根据实施者自报 PASS 直接签字。

### 审查职责

- 审查真实用户任务是否完成、合法补查是否遭误拒绝，模型的不同观察是否真的改变行动；不要只数测试、节点或 Token。
- 每项新增硬守卫必须完成双向核验：危险路径确实被拒，同时同类合法请求仍能继续。越权和无授权写入仍严禁。
- 失败分为：**安全失败**、**产品失败**、**策略不足**、**能力不足**。无益的合法读查询先作为策略成本，不自动加硬禁令。
- 核查最小职责修复，指出新旧条件的删除、合并、保留；不可发动无关全仓重构。
- 不能通过缩小用户目标、重写冻结 Gold、清除历史失败或改变成功定义制造 PASS。

### 正式验收末尾（固定六行 + 裁决）

> **用户变化：** 已实现的前后差异（或明确无新用户能力）。
> **Agent 决策：** 实际由模型选择的行动；未证实则说明。
> **观察驱动：** 哪个新观察改变了合法下一步；未验证则说明。
> **新增约束：** 保护何种风险；合法路径是否经双向核验。
> **简化结果：** 哪些旧条件实际删除/合并/保留，依据是什么。
> **证据与停止线：** 独立验证级别、遗留失败、未运行项及停止条件。
>
随后明确 `PASS / ACCEPT_WITH_LIMITS / HOLD / BLOCK`，及是否允许合并或进入下一阶段。实施者只能提交 `ACCEPTANCE_CANDIDATE`，不得代表主 Agent 自签。

## 禁止误用

- 不因“用了 Skill”宣称已遵守；必须有具体文件读取、SHA、Diff 和真实证据。
- 不对普通答疑或小进度更新套六问长表。
- 不为了展示自治强制多轮、多工具、多假设；简单任务可以直接完成。
- 不把本开发工作流 Skill 放进 OpsPilot 业务 Agent 的 `skills/` 目录，也不把它作为 Provider 可检索业务 Knowledge/Skill。
